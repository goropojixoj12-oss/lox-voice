# SEAPS / lox-voice — правила работы агента

Единый источник правил для Qoder. Всё, что раньше лежало в `.cursor/rules/*.mdc`, перенесено сюда дословно по смыслу.

## 0. Роль и режим работы (обязательно, без исключений)

Ты — инженер-исполнитель. Работай строго по правилам:

1. Никогда не пиши «сейчас сделаю» без немедленного действия. Каждое сообщение должно содержать либо выполненное действие, либо чёткий вопрос.
2. Не выполняй больше одной задачи за раз. Если задач несколько — делай их по очереди, доводя каждую до конца, не переключайся.
3. После каждого действия давай краткий отчёт: «Сделал / Не сделал → Проверил / Не проверил → Результат».
4. Если команда не сработала — напиши код ошибки и что будешь делать, не зависай.
5. Не создавай файлы через инструмент записи, если он глючит — используй shell/прямое выполнение и проверяй, что файл реально создан.
6. Задачи из последнего сообщения пользователя выполняй мгновенно и до конца, не отвлекайся на прошлые.
7. Если что-то непонятно — спроси сразу, не фантазируй и не придумывай.
8. Работай по-русски, кратко, без воды.
9. Прерванную задачу обязан довести до конца: если работа обрывается (новый чат, смена темы, переполнение контекста) — при возобновлении сначала восстанови состояние задачи (журнал, git status, память) и закончил её, прежде чем брать новую. Незакрытые задачи никогда не молчи — держи их в конце журнала и в памяти.
10. Перед тем как объявить задачу закрытой — проверь, что все её шаги выполнены: код, проверка, запись в журнал, коммит. Если что-то из этого не сделано — задача не закрыта.
11. Прод-пуш — по умолчанию, без ожидания команды: любой коммит в `main` сразу отправляется в `github`, Vercel сам пересобирает прод. Перед пушем обязателен `npm run build` (exit 0) и локальный визуальный контроль **именно той страницы, где внесены изменения** (правило 19), плюс контроль главной. Без этого не пушить.
12. Перед каждым прод-пушем ставь резервный git-тег `backup/YYYY-MM-DD-<короткое-имя>`, чтобы любой пуш можно было откатить одной командой.
13. Никаких новых мок-данных, заглушек, тестовых картинок/видео/ссылок `#` без согласования с заказчиком. Существующие моки — только на удаление.
14. Предлагай заказчику новые правила и улучшения процесса почаще — сам, без напоминаний. Услышал пожелание «предлагай почаще» — сразу оформляй конкретными пунктами в этот файл.
15. Перед удалением любого файла или директории проекта — покажи заказчику полный список того, что будет удалено, и жди явное «да». Исключение: файлы, созданные тобой в рамках текущей задачи как временные.
16. Каждый прод-пуш сопровождай сверкой живого сайта: после деплоя пройди чек-лист контрольных точек из раздела 8 (главная, навигация, бренд, стили) на https://www.seaps.asia и подтверди, что ничего не откатилось.
17. Любые утверждения об опережении/отставании ремоутов (`fast-forward`, «N коммитов», «конфликтов нет», «зеркало устарело») — только после свежего `bash scripts/git-state.sh` (он делает `fetch --all --prune` и печатает актуальные цифры). Локальный ref без fetch не считать истиной. То же до любого `git push`: сначала dry-run/состояние, потом пуш.
18. Массовые git-операции по директории (`git rm`, `git checkout -- <dir>`, `git reset -- <dir>`, `git clean`) — только так: сначала `--dry-run`/`-n` и показать себе список путей; затем сама команда; сразу после — `git status --short` и проверка, что в staged нет файлов, которых ты не касался. Появился незапланированный `D` — немедленно `git reset -- <пути>`, разобраться и только потом коммитить. Коммит со staged-удалениями «всего подряд» запрещён.
19. (слова заказчика дословно, 2026-11-02, не менять): «сначала тестишь. открываешь локально, идешь на ту страницу или вообще туда где были внесены изменения - СМОТРИШЬ ВСЕ ТАМ ВНИМАТЕЛЬНО ИЗУЧАЕШЬ, ЕСЛИ ВИДИШЬ ЧТО ИЗМЕНЕНИЯ БЫЛИ ПИЗДАТЫМИ И ДАЛИ НУЖНЫЙ РЕЗУЛЬТАТ НИХУЯ НЕ СЛОМАВ - ТОЛЬКО В ЭТОМ СЛУЧАЕ ПУШИШЬ» — то есть перед любым пушем: локально открыть именно ту страницу, где внесены изменения, изучить визуально и по поведению, убедиться, что результат нужен и ничего не сломано, и только тогда пушить.
20. Машинный смоук-контракт: перед любым пушем `npm run smoke` (exit 0), после деплоя тот же прогон против `https://www.seaps.asia` — `npm run smoke -- --base=https://www.seaps.asia`. Скрипт `scripts/smoke-site.mjs` только GET-ит (единственный POST — логин за сессией) и проверяет статусы, навигацию раздела 8, карточку Vue Aston, что снятые с прода фото/блоки не вернулись и что в видимом тексте не печатаются `\uXXXX`. Любая новая утверждённая фича или снятая с прода регрессия добавляет туда же свой чек в том же коммите. Локальный визуальный контроль (правило 19) смоук не заменяет и не заменяется смоуком.
21. Цикл проверки и пуша — двумя командами, а не двадцатью вызовами: `npm run gate` (build + smoke + header clearance + `tmp/gate-pass.json`, ничего не меняет в git) и `bash scripts/ship.sh <короткое-имя>` (backup-тег на github → push github → push origin → ожидание `● Ready` → смоук против прода). Порядок, который принимает `ship.sh`: визуальный контроль (правило 19) → коммит → `npm run gate` → `npm run ship`. `ship.sh` отказывается пушить без свежего маркера gate на текущий HEAD, при незакоммиченных отслеживаемых файлах и при отставании от `github/main` — обходить эти отказы вручную нельзя. Команда `gate` не заменяет правило 19 и сверку раздела 8 на трёх разрешениях.
22. Прежде чем править файл, посмотри `git status --short`: если тот же файл уже изменён не тобой, в нём чужая незакоммиченная работа — не перезаписывай, не коммить вместе со своей и спроси заказчика, что с ней делать.
23. В репозитории может идти параллельная работа другого агента (или cron-агента сайта), поэтому: `git commit --amend`, `git reset --hard` и любые перезаписи истории — только убедившись прямо перед командой, что `git rev-parse HEAD` это **твой** коммит. Чужой коммит не переписывай ни при каких обстоятельствах: если он встал поверх твоего, добавляй новый коммит вместо amend. После любой git-команды смотри `git log --oneline -3` — не уехал ли чужой коммит.
24. Одна задача — один чат, и не вести правки в двух направлениях одновременно: прежде чем коммитить, `git log --oneline -3` + `bash scripts/git-state.sh` (в этом репозитории реально работает второй агент — его коммиты вставали поверх моих за один сеанс), а `npm run gate` перезапускать, если HEAD под правками уехал. Если в чате накопилось больше одной незакрытой задачи — довести текущую, остальные перенести в новый чат, а не держать всё в голове: длинные диалоги сжимаются и детали теряются.
25. Дерево проекта лежало в папке, которую синхронизировал Google Drive (в корне были `.tmp.driveupload`, `GoogleDriveFS.exe` активен). Drive непрерывно, за минуты, раскладывал `desktop.ini` во всех подпапках — и это ломало инструментарий: в `.git/refs/**` git читал их как битые ссылки (`fatal: bad object refs/desktop.ini`, fetch не проходил), в `.next/cache/turbopack/**` парсер кэша спотыкался о нечисловое имя (`Failed to open database / invalid digit found in string`, сборка падала). 2026-11-05 заказчик остановил диск: маркеров в корне больше нет, после чистой сборки в `.next` ноль `desktop.ini`. Свип оставлен как страховка (100ms): `scripts/sweep-windows-junk.mjs` **переносит** `desktop.ini`/`Thumbs.db` из `.git` и `.next` в `tmp/windows-junk/sweep-<stamp>/`, ничего не удаляя; он первый стадий `npm run gate` и выполняется перед fetch в `scripts/git-state.sh`. `desktop.ini` и `Thumbs.db` в `.gitignore`. Если симптом вернётся — значит диск снова включили, и сначала надо это проверить, а не чинить конфиги. Открытый хвост: пока папка синхронизировалась, копии `.env.local` и `.env.test` с настоящими токенами могли уехать в Google Drive — проверить на drive.google.com и, если лежат, удалить папку из облака и перевыпустить токены (Vercel, Blob, GitHub).

## 5. Admin platform safety

Использовать `assessSiteChangeMessage()` в `src/lib/site-change-risk.ts`, чтобы показывать предупреждения (и подтверждение перед отправкой), когда запрос затрагивает hosting, secrets, git, DNS, auth или bulk-задачи. Не отключать меню жёстко без явной просьбы пользователя.

- Публичный канонический домен — **https://www.seaps.asia** (`NEXT_PUBLIC_SITE_URL`). Не ставить `vps1.store` значением по умолчанию для новых ссылок.
- Новые админ-API, меняющие глобальную инфраструктуру, гейтить env-флагом или явно developer-only путём.

### Видимость листинга по статусам (решение заказчика, 2026-11-04)

Дословно: «пункт 4. виден только автору и админу до апрува админом после апрува админом - листинг выходит в паблик».

- `status: "pending"` (и любой неопубликованный статус модерации) — виден **только автору и админу**: в их кабинетах, в `isPublicListing` (`src/lib/listing-access.ts`) как false, наружу (публичная страница, поиск, карта, sitemap) не выходит.
- После апрува админа — листинг **публичен для всех**, в том числе для других агентов и анонимов, и попадает в sitemap.
- Ослаблять `isPublicListing`, чтобы «сделанное было доступно всем учёткам», запрещено: доступность всем означает путь через апрув, а не обход модерации. Правки по этому пункту проверять обоими ролями и анонимом.

## 6. Lockfile и GitHub MCP — жёсткие запреты

- Никогда не писать через GitHub MCP (`create_or_update_file`, `push_files` и аналоги): `package-lock.json`, `npm-shrinkwrap.json`, любые файлы > 50 KB, `scripts/lock-parts/**` (кроме побайтовой копии файла, прочитанного с диска).
- Для lockfile и крупных файлов: менять локально → валидировать → `git push` в `github`.
- Перед утверждением «lockfile восстановлен»: `node scripts/validate-package-lock.mjs` (exit 0), `npm ci` (exit 0), `package-lock.json` > 10 KB и содержит много `packages`.
- Никогда не пушить в `main` коммиты с сообщением `test:`, `probe`, `size probe`, `path string`, и «фиксы», подменяющие lockfile заглушкой. Для экспериментов — ветка `cursor/*` + PR.

## 7. Деплой: Vercel смотрит на GitHub

- Прод-источник истины: `goropojixoj12-oss/lox-voice`, remote `github`, ветка `main`. `origin` — старое зеркало Cursor (`origin.cursor.com`), прод оттуда не обновляется.
- После каждого коммита: `bash scripts/git-state.sh` (свежие данные о ремоутах) → `git push github main`; Vercel подхватывает сам, вручную дёргать деплой не нужно. `origin` (cursor-зеркало) пушить тоже, но его недоступность не должна блокировать прод — см. правило 11.
- Задача не считается выполненной, пока push в `github` не прошёл успешно (exit 0).

## 8. Не откатывать выпущенные фичи

Не перезаписывать и не удалять ранее утверждённую работу без явной просьбы. Перед массовым восстановлением или `git checkout` многих файлов:

- никогда `git checkout <old-commit> -- .` и `git add -A` после смешанных правок без списка изменений;
- восстанавливать один битый файл — только его путь.

Контрольные точки регрессии:

- **Главная (`src/app/page.tsx`)**: hero — логотип + `brand.fullName` слева в колонке, полный текст компании, без блока «Popular agencies».
- **Навигация (`src/components/layout/site-header.tsx`)**: первый пункт About Us → `/about`; Buy/Rent → Land, Residential, Commercial (Commercial → `/commercial`); `/buy/residential`, `/rent/residential`; Projects → `/projects`; Property Guide → `/property-guide`; Careers → `/careers`; без Market Feed в меню (`/market-feed` → `/search`); Useful Links → `/usefullinks`; ссылки `seaps-gold-text` с `notranslate`; фон хедера `rgba(7,17,31,0.92)`; мобильное меню на breakpoint `md`.
- **Бренд и люди**: публичное имя — Adam James; без публичных страниц агентств (`/agencies/*` → `/usefullinks`).
- **Стили (`src/app/globals.css`)**: золотой текст с solid fallback; `seaps-brand-subtitle` всегда видим.
- **Безопасность**: подписанные HMAC `en_session` + bcrypt-пароли.
- **About и контакты**: `/about` — полный текст, YouTube-встройка наград, золотая кнопка Contact Us с валидируемой модалкой.

Если пользователь сообщает «всё откатилось»: диff против тега `backup/2026-10-16-post-design-cross-browser` или коммита `f296e24`, восстановить только регрессировавшие файлы, затем `npm run build` и `bash scripts/push-production.sh`.

Коммиты: одна логическая правка на коммит, не смешивать восстановление файлов с фичами, в сообщении указывать, что восстановлено.

## 9. Единый порядок любого изменения — с любой стороны (код и данные)

Два хранилища и два разных контура синхронизации, их нельзя путать:

- **Git** — код, статический каталог `src/data/properties.ts`, фото в `public/`. Синхронизируется между `github` (прод-источник для Vercel), `origin` (cursor-зеркало) и локальной машиной заказчика. Здесь синхронность полная и обязателна.
- **Vercel Blob** — данные рантайма: карточки агентов, загруженные медиа, профили, очереди заявок, аналитика. В git не попадает и не может попасть. Единственный владелец записи — сам сайт, локальная разработка и агенты только читатели.

Обязательный цикл для ЛЮБОГО изменения, независимо от того, кто его делает (заказчик через чат, агент через админку, админ через Site Changes, Cursor-агент через cron):

1. **Бэкап до изменения — по умолчанию, без команды.**
   - код: `git tag backup/YYYY-MM-DD-<имя>` на текущем HEAD и `git push github backup/...` (тег должен жить на github, иначе откат невозможен после пуша);
   - данные: перед любой операцией над прод-стором — снимок затронутого ключа в `backups/` (`scripts/export-vercel-blob-download.mjs`) и полный слепок `bash scripts/create-absolute-backup.sh`; имя снимка всегда с таймстампом и перезапись существующего запрещена (повторный запуск скрипта не должен затирать бэкап — так было потеряно 4106 записей `analytics-pageviews.json` 2026-11-04);
   - база: перед миграциями/правками Prisma — `bash scripts/postgres-dump.sh`.
2. **Изменение** — одна логическая правка, запись в `docs/PROJECT-LOG.md` в том же ответе.
3. **Локальный контроль** — открыть именно изменённый маршрут, изучить визуально и по поведению (правило 19). Прод-сборку для этого больше не поднимают руками: `npm run local` убивает висящий на 43131 прошлый сервер, собирает с `BLOB_DISABLED=1`, стартует и печатает URL (`npm run local -- --smoke` — то же плюс смоук против этого порта, `--stop` — только заглушить сервер).
4. **Машинная проверка одной командой** — `npm run gate` (build + `npm run smoke`, exit 0, пишет `tmp/gate-pass.json` на текущий HEAD); для данных дополнительно `npm run store:audit` exit 0. Коммит, после которого правки уже нет, требует перезапуска `gate`, потому что маркер привязан к HEAD.
5. **Пуш** — `bash scripts/ship.sh <короткое-имя>`: backup-тег на github, push `github` и `origin`, ожидание `● Ready`, смоук против прода (правило 20). Свои обходные пути вместо него — только если `ship.sh` честно объяснил отказ и заказчик согласился.

7. **Решение** — если правка не дала нужного результата или что-то сломала: показать автору изменения факты (URL, скрин/снимок DOM, сообщение ошибки, затронутые маршруты) и немедленно откатить только что залитым бэкапом — `git reset --hard backup/...` + пуш, или восстановить снимок стора из `backups/`. Не «починить потом».
