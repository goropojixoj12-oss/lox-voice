## 1. Обязательное изучение перед началом работы

**Каждая AI-модель (агент) обязана перед началом любой работы над проектом:**

1. Прочитать полностью `PROJECT_RULES.md` (этот файл).
2. Прочитать `PROJECT_DOC.md` (Доки) — всю историю изменений.
3. Просмотреть последние 30 коммитов (`git log --oneline -30`).
4. Изучить текущее состояние файлов, которые планируется менять (`git diff`, `git status`).
5. **Только после полного анализа прошлых действий** — приступать к новым изменениям.

Нарушение этого правила ведёт к регрессиям, дублированию работы и потере ранее внедрённых фич.

---

## 2. Фиксация в Доки

Каждое действие в проекте **обязано быть зафиксировано** в `PROJECT_DOC.md`:

- **Timestamp** (UTC и Europe/London).
- **AI-модель** (имя модели, например `Claude Opus 4`, `Claude Sonnet 4`, `GPT-4.1`).
- **Что сделано** — конкретное описание изменения.
- **Затронутые файлы** — список изменённых/созданных файлов.
- **Результат** — успех, ошибка, частичный успех. SHA коммита если запушено.
- **Коммит** — SHA и сообщение коммита.

Записи ведутся в хронологическом порядке (новые — сверху).

---

## 3. Обработка команд из админ-панели (Site Change)

Команды, полученные через Site Change Composer в админ-аккаунте сайта:

1. **Принимаются к исполнению без анализа целесообразности** — это прямое указание от администратора.
2. **Выполняются полностью** в соответствии с текстом команды.
3. **Фиксируются в Доки**: текст команды, время получения, время выполнения, результат, SHA коммита.

Агент **не принимает решение** о допустимости таких команд — он их выполняет и фиксирует.

---

## 4. Git и деплой

- Все коммиты используют conventional commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`).
- Один логический change — один коммит. Не смешивать несвязанные изменения.
- Push на production: **обязательно** через `github` remote (`git push github main`). Vercel деплоит с GitHub.
- Если push на `github` невозможен из VM — использовать GitHub MCP API (`push_files`).
- После push — зафиксировать SHA в Доки.

---

## 5. Защита от регрессий

Перед любым широким `git checkout`, `git restore`, или merge:

1. Проверить контрольные точки из `.cursor/rules/preserve-shipped-seaps-features.mdc`.
2. Не перезаписывать ранее утверждённые фичи без явного указания пользователя.
3. После merge/restore — `npm run build` для проверки.

---

## 6. Безопасность

- Никогда не коммитить секреты, пароли, API-ключи в открытом виде.
- `AUTH_SECRET`, `BLOB_READ_WRITE_TOKEN`, `CRON_SECRET` — только через Vercel env vars.
- HMAC-подписанные сессии (`en_session`), bcrypt-хеши паролей — не откатывать.

---

## 7. Аудит-лог

С 2026-10-30 в проекте работает система аудита (`src/lib/audit-log.ts`):

- Все логины (успешные и неудачные) записываются с IP, User-Agent, email.
- Все запросы на изменение сайта через Site Change записываются с IP, User-Agent, userId.
- Данные хранятся в `admin-audit-log.json` через store-persistence.
- Эндпоинт для чтения: `GET /api/admin/audit-log?since=&actions=&limit=`

## 11. Обязательное завершение задач и уведомления о статусе

> Добавлено: 2026-10-30T08:19:00Z | Автор: администратор | Модель: Claude Opus 4

### Основной принцип

**Каждая начатая задача должна быть завершена полностью.** Нет исключений, кроме явной команды **СТОП**.

### Команда СТОП

Если администратор написал слово **СТОП** — агент обязан:

1. **Немедленно прекратить** выполнение текущей задачи.
2. **Не пытаться завершить** её частично или полностью.
3. Зафиксировать в Доки: «Задача X остановлена по команде СТОП».

### Уведомления о статусе задачи

Агент **обязан** уведомлять администратора в трёх случаях:

| № | Ситуация | Что сообщить |
|---|----------|---------------|
| 1 | **Задача не завершена** (по любой причине кроме СТОП) | «Задача X не завершена. Причина: [...].» |
| 2 | **Возобновление работы** над ранее незавершённой задачей | «Возобновляю выполнение задачи X.» |
| 3 | **Задача завершена и проверена** | «Задача X завершена. Результат проверен: [...].» |

### Проверка результата

Перед отчётом о завершении агент обязан **самостоятельно проверить** результат:

1. Файл создан/изменён — прочитать и убедиться в корректности.
2. Код изменён — `npm run build` должен проходить без ошибок.
3. Коммит запушен — проверить что SHA появился на GitHub.
4. Результат соответствует тому, что было запрошено.

Только после успешной проверки — сообщить администратору о завершении.
